# AS-IS: диагностика текущей архитектуры AdScale

## Шаг 1. Рамка анализа

**Объект:** платформа AdScale в текущем состоянии (AS-IS).
**Цель:** выявить ограничения текущей архитектуры, из-за которых не выполняются целевые показатели SLA (P95 ≤100 мс для аукциона и ≤80 мс для DSP при росте до 18 000 RPS) и блокируется масштабирование до 50 000 RPS.
**Вопросы анализа**:
1. Где узкие места (bottlenecks)?
2. Где точки отказа (SPOF)?
3. Что препятствует масштабированию?
4. Как текущая архитектура влияет на время отклика?

**Источники:** C4 Container-диаграмма, профиль нагрузки и метрики, перечень компонентов и ограничений.


## Шаг 2. Моделирование AS-IS через C4

Диаграмма AS-IS приведена в задании.

**C4 Container:** монолит из 7 компонентов + одна PostgreSQL. Диаграмма покрывает и контекстный уровень — на ней присутствуют акторы (рекламодатель, пользователь) и внешние системы (DSP-партнёр, платёжный шлюз).

**Компоненты монолита:**

| Компонент | Технология | Ответственность |
|---|---|---|
| **Ad Server** | C++, Go | Принимает HTTP-запросы, определяет пользователя, подбирает кандидатов |
| **Auction Engine** | C++ | Взвешивание ставок, бизнес-правила, расчёт победителя |
| **Delivery Service** | Node.js | Формирует HTML/JS-разметку баннера и HTTP-ответ |
| **Statistics Service** | Python | Запись кликов и показов |
| **Financial Service** | Go | Списание средств, выставление счетов, управление балансами |
| **Analytics Service** | Python | Аналитические SQL-запросы по production-БД |
| **Advertiser Dashboard** | Node.js + JavaScript | Web UI: управление кампаниями, отчётность |

**Хранилище:**

| Хранилище | Технология | Ответственность |
|---|---|---|
| **PostgreSQL** | PostgreSQL (одна инстанция) | Единая БД: кампании, ставки, события, финансы, аналитика |

**Направления потоков (как на диаграмме):**

| Откуда → Куда | Объект данных | Способ |
|---|---|---|
| DSP-партнёр → Ad Server | Bid-requests / responses | HTTPS / OpenRTB |
| Пользователь → Delivery Service | Просмотр рекламы и клики | HTTPS |
| Рекламодатель → Advertiser Dashboard | Управление кампаниями и бюджетами | HTTPS |
| Financial Service → Платёжный шлюз | Пополнение бюджета | HTTPS / REST |
| Ad Server → Auction Engine | Передаёт кандидатов | Internal Call |
| Auction Engine → Delivery Service | Передаёт победителя аукциона | Internal Call |
| Delivery Service → Statistics Service | Регистрирует показы/клики | Internal Call |
| Advertiser Dashboard → Financial Service | Управление финансами | Internal Call |
| Advertiser Dashboard → Analytics Service | Запросы аналитики | Internal Call |
| Auction Engine → PostgreSQL | Читает ставки и кампании | JDBC / Sync |
| Statistics Service → PostgreSQL | Прямая запись событий | JDBC / Direct Write |
| Financial Service → PostgreSQL | Транзакции и балансы | JDBC |
| Analytics Service → PostgreSQL | Тяжёлые аналитические запросы | JDBC |
| Advertiser Dashboard → PostgreSQL | CRUD-операции | JDBC |
| Ad Server → PostgreSQL | Чтение данных для таргетинга | JDBC |

**Обозначения способов (по диаграмме):**
- `Internal Call` — внутренний вызов между компонентами монолита;
- `JDBC` — обращение к PostgreSQL;
- `JDBC / Sync` — синхронное обращение к БД;
- `JDBC / Direct Write` — прямая запись в БД;
- `HTTPS / OpenRTB` — внешний обмен с DSP по протоколу OpenRTB;
- `HTTPS / REST` — внешний REST-вызов.

## Шаг 3. Сбор фактов

Источники фактических данных: статика (код/документация), экспертное знание (интервью),
динамика (метрики/логи/трейсы), граничные условия (нагрузочное тестирование).

### 3.1 Динамика: метрики и профиль нагрузки
- **15 000 RPS** в пике; запаса по производительности нет.
- **P95 110–120 мс** при требовании **≤100 мс**; периодические деградации в часы пик.
- Высокая **нагрузка на запись** (клики/показы), **постоянный поток событий**.

### 3.2 Статика: стек и инфраструктура
- Гибридный монолит (C++/Go/Python/Node), **одна PostgreSQL**, общая схема.
- **Нет кеша, нет очередей, нет контейнеризации**, ручной деплой, один production-кластер.

### 3.3 Путь обработки bid-request (по диаграмме)

| Шаг | Откуда → Куда | Объект данных | Способ |
|---|---|---|---|
| 1 | DSP-партнёр → Ad Server | Bid-request | HTTPS / OpenRTB |
| 2 | Ad Server → PostgreSQL | Чтение данных для таргетинга | JDBC |
| 3 | Ad Server → Auction Engine | Передаёт кандидатов | Internal Call |
| 4 | Auction Engine → PostgreSQL | Читает ставки и кампании | JDBC / Sync |
| 5 | Auction Engine → Delivery Service | Передаёт победителя аукциона | Internal Call |
| 6 | Delivery Service → Statistics Service | Регистрирует показы/клики | Internal Call |
| 7 | Statistics Service → PostgreSQL | Прямая запись событий | JDBC / Direct Write |
| 8 | Ad Server → DSP-партнёр | Bid-response (возврат по той же связи) | HTTPS / OpenRTB |

**Факт:** к PostgreSQL на диаграмме подключены **6 компонентов** (Ad Server, Auction Engine,
Statistics, Financial, Analytics, Dashboard). В пути **одного bid-request** используется **3 из них**:
2 чтения (Ad Server, Auction Engine) и 1 прямая запись (Statistics) — все через JDBC, внутри бюджета ≤100 мс.
Остальные 3 (Financial, Analytics, Dashboard) не участвуют в bid-request, но работают с **той же БД**
и создают конкуренцию. Запись события стоит **в том же пути**, что и ответ аукциона.

**Результат этапа:** зафиксировано наблюдаемое состояние системы — метрики (15 000 RPS, P95 110–120 мс),
стек и инфраструктура, путь обработки bid-request. Экспертные интервью и нагрузочное тестирование
в исходных данных отсутствуют — выводы строятся на данных ТЗ и диаграмме.

## Шаг 4. Антипаттерны

Выделяются пять классов архитектурных проблем.

### 4.1 Узкие места (bottlenecks)
- **Auction Engine** (сервис ставок) — обращение к PostgreSQL через `JDBC / Sync` в пути обработки bid-request → основной вклад во время отклика; при росте нагрузки растёт **вероятность тайм-аутов** и сбоев.
- **Ad Server** — обращение к PostgreSQL (`JDBC`) для чтения таргетинга в том же пути.
- **Statistics Service** — прямая запись событий (`JDBC / Direct Write`) без буферизации → высокая нагрузка на запись, конкуренция с транзакциями.
- **Analytics Service** — тяжёлые SQL (`JDBC`) напрямую на production-БД без read replica → блокировки, рост времени отклика.
- **Financial Service и Advertiser Dashboard** — работают с той же PostgreSQL (`JDBC`): транзакции и CRUD создают дополнительную конкуренцию с путём обработки bid-request.

### 4.2 Единые точки отказа (SPOF — Single Point of Failure)
- **Единственная PostgreSQL** — нет **HA** (High Availability — высокая доступность) и реплик; её отказ останавливает всё. С ней работают **все 6 компонентов** (Ad Server, Auction Engine, Statistics, Financial, Analytics, Dashboard).
- **Монолит в одном процессе** — отказ/редеплой затрагивает все функции сразу.

### 4.3 Низкая эластичность
- **Нет запаса по производительности** — система работает на пределе (15 000 RPS), резерва нет.
- Вызовы `Internal Call` и `JDBC / Sync` блокируют потоки; **нет очередей** для буферизации пиков.
- **Нет кеша** — каждый запрос идёт в БД.
- Нельзя масштабировать отдельные компоненты (сервис ставок) независимо.

### 4.4 Технический долг
- Монолит: любое изменение → редеплой всей системы.
- **Нет контейнеров и CI/CD**, ручной деплой → медленные и рискованные релизы, нет быстрого rollback.
- **Один production-кластер**, нет географического резервирования.
- Архитектура не задокументирована; нет SRE (Site Reliability Engineer), BA (Business Analyst) и технического писателя.

### 4.5 Скрытые зависимости
- **Общая схема БД**: модули обращаются к одним и тем же таблицам напрямую, поэтому изменение
  таблицы кампаний/ставок ломает отчёты и другие модули.
- **Прямые Internal Call между модулями** (Ad Server → Auction Engine → Delivery → Statistics):
  изменение контракта одного модуля затрагивает всю цепочку.

## Шаг 5. Количественная оценка

**Норма:** P95 ≤100 мс для аукциона, ≤80 мс для DSP-партнёра.

| Сценарий | RPS | P95 времени отклика | Оценка |
|---|---|---|---|
| Сейчас | 15 000 | 110–120 мс | выше нормы, запаса нет |
| +DSP (3 мес) | 18 000 | прогноз **>150 мс** | риск тайм-аутов, сбоев сервиса ставок, штрафы DSP |
| Год | 50 000 | нежизнеспособно | нужна новая архитектура |

**Вывод:** система **не масштабируется линейно** — при росте с 15 000 до 18 000/50 000 RPS время
отклика деградирует нелинейно. Путь обработки bid-request синхронно обращается к единственной PostgreSQL
(Ad Server, Auction Engine), а ту же БД нагружают запись событий (Statistics) и тяжёлая аналитика
(Analytics); кеша и очередей нет, отдельные компоненты масштабировать нельзя (монолит). Без изменений
SLA не выполняется: P95 выше 100 мс уже сейчас, при 18 000 RPS — риск деградации свыше 150 мс
и тайм-аутов, к 50 000 RPS архитектура нежизнеспособна.

## Шаг 6. Причинно-следственная модель

| Симптом (наблюдаемый) | Причина (архитектурная) |
|---|---|
| Высокий P95 (110–120 мс при норме ≤100) | Обращения к PostgreSQL через `JDBC / Sync` в пути обработки bid-request; нет кеша |
| Деградация в часы пик | Конкуренция за единственную БД (транзакции + аналитика + события) |
| Сбои сервиса ставок | Перегрузка Auction Engine и тайм-ауты БД |
| Ограничение масштабирования (нет запаса) | Монолит + единая БД |
| Конкуренция за ресурсы БД | Все 6 компонентов работают с одной PostgreSQL по общей схеме |

## Шаг 7. Переход к гипотезам

| Причина | Гипотеза |
|---|---|
| Обращения к PostgreSQL через `JDBC / Sync` в пути обработки bid-request | Кеш (Redis) + вынос сервиса ставок из монолита |
| Прямая запись событий (`JDBC / Direct Write`) | Асинхронная обработка (Kafka) |
| Тяжёлая аналитика на production-БД | Отдельное хранилище для аналитики (OLAP — аналитическая обработка запросов) |
| Единственная PostgreSQL как точка отказа | Database per service (своя БД у каждого сервиса) + репликация |
| Монолит | Strangler Fig (постепенное вырезание из монолита) |

Гипотезы проверяются в `TO-BE.md` и ADR (`adr/`).
