# ADR-001: Переход к микросервисам выполняется по стратегии Strangler Fig

- **Статус:** Принято
- **Дата:** 2026-10-26

## Контекст

AdScale — монолит на одной PostgreSQL, работает на пределе возможностей. Впереди подключение крупной
DSP-площадки: нагрузка вырастет на 20%, а через год — вдвое. Полная переработка невозможна,
бюджет ограничен, срок — три месяца, непрерывность бизнеса обязательна.

**Ключевые архитектурные драйверы:**
- **Нагрузка:** 15 000 RPS сейчас, 18 000 после подключения DSP, 50 000 через год.
- **Время отклика:** P95 110–120 мс при норме ≤100 мс для аукциона и ≤80 мс для DSP.
- **Доступность:** SLA 99.9% (целевое состояние).
- **Сроки:** 3 месяца до подключения DSP.
- **Команда:** 35 человек; нет SRE, бизнес-аналитика и технического писателя.
- **Бюджет:** ограничен — нарастить команду нельзя.
- **Непрерывность:** платформу нельзя останавливать (штрафы DSP за простои).

Рассматривались четыре альтернативы.

### Альтернатива 1. Оставить монолит и только оптимизировать

**Плюсы:** минимальные изменения, быстрый срок, не нужно менять инфраструктуру и процессы.

**Минусы:** не решает атрибуты качества — нет независимого масштабирования критического пути,
сохраняется конкуренция за одну БД с аналитикой и статистикой, SLA ≤100 мс не достигается.

### Альтернатива 2. Единовременная замена (big-bang) на микросервисы

**Плюсы:** сразу целевая архитектура, нет переходного периода с двойной логикой.

**Минусы:** высокий риск срыва 3-месячного срока и непрерывности; нет SRE, CI/CD и контейнеризации;
бюджет не позволяет; ошибка затрагивает всю платформу сразу.

### Альтернатива 3. Модульный монолит (границы внутри приложения)

**Плюсы:** дешевле и быстрее, сохраняются ACID-транзакции, наводит порядок в границах модулей.

**Минусы:** остаётся один процесс и одна БД — не даёт выигрыша по времени отклика и не позволяет
масштабировать сервис ставок независимо; до 50 000 RPS не доводит.

### Альтернатива 4. Strangler Fig (выбрано)

**Плюсы:** постепенное замещение с откатом на каждом шаге, монолит продолжает работать,
инфраструктура вводится по мере необходимости, непрерывность сохраняется.

**Минусы:** переходный период с dual-run и дублированием логики; нужна дисциплина миграции данных.

## Решение

Переход выполняется по стратегии **Strangler Fig**: функциональность постепенно выносится из монолита
в отдельные сервисы за фасадом API Gateway. Переключение — через **feature flags**, **canary**
(1–5% трафика) и **shadow-трафик** (дублирование запросов без отдачи клиенту). Монолит остаётся
работоспособным до полного переключения.

Порядок выноса — по приоритету нагрузки и с учётом срока:
- **К 3 месяцам:** API Gateway → Bidding Service → Statistics Service (Kafka) → Analytics Service (read replica).
- **Этап 2 (4–9 месяцев):** Kubernetes, ClickHouse, Financial Service, Campaign Service, Delivery Service.
- **Год:** service mesh, мультирегион.

Каждый шаг обратим: при деградации трафик возвращается в монолит флагом.

## Последствия

**Положительные:**
- низкий риск: каждый шаг обратим, монолит продолжает работать;
- соответствует сроку и бюджету;
- инфраструктура (Kafka, Redis, API Gateway) вводится постепенно;
- непрерывность бизнеса сохраняется.

**Отрицательные:**
- переходный период требует dual-run и дублирования логики;
- нужна дисциплина миграции данных (dual-write / CDC);
- временно усложняется эксплуатация: работают и монолит, и новые сервисы.

**Риски:**
- Если за 3 месяца не удастся вынести Bidding Service, DSP подключается к монолиту с деградацией SLA
  и штрафами по контракту.
- Dual-write может привести к расхождениям данных между монолитом и сервисом — нужна сверка.
- Рост операционной сложности без SRE: часть нагрузки по эксплуатации ложится на DevOps-команду.
