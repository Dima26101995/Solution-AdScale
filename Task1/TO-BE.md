# TO-BE: целевая архитектура AdScale

## 1. Выбор архитектурного стиля

### 1.1 Почему не оставить монолит
Монолит исчерпал ресурс: 15 000 RPS в пике, P95 110–120 мс при норме ≤100 мс, деградации в часы пик.
Оставить его нельзя по четырём причинам:
1. **SLA не выполняется уже сейчас.** Синхронные обращения к БД в пути обработки bid-request
   не позволяют уложиться в 100 мс (для DSP — 80 мс), а после подключения DSP нагрузка вырастет до 18 000 RPS.
2. **Критичные и некритичные потоки не разделены.** Путь обработки bid-request конкурирует за ту же
   БД и CPU с аналитикой и статистикой — требование промежуточного решения невыполнимо в монолите.
3. **Нельзя масштабировать отдельные компоненты.** Горизонтально масштабируется только всё приложение
   целиком, хотя нагружены в первую очередь **Ad Server** и **Auction Engine**; отсутствие запаса не даёт дойти до 50 000 RPS.
4. **Единственная БД — точка отказа** (нет HA и реплик), а транзакционная и аналитическая нагрузка
   смешаны в одном хранилище; любое изменение требует редеплоя всей системы.

### 1.2 Почему не переписать сразу на микросервисы
Полная переработка в микросервисы сразу неприемлема:
1. **Срок и бюджет.** За 3 месяца нужно разрезать 7 компонентов, перенести данные и не остановить
   бизнес; бюджет не позволяет нарастить команду.
2. **Незрелость инфраструктуры.** Нет контейнеризации, CI/CD, мониторинга и трассировки; один
   production-кластер — распределённую систему нечем разворачивать и эксплуатировать.
3. **Нет границ для разрезания.** Архитектура не задокументирована, домены не выделены; разрезать
   «по факту» без анализа означает получить распределённый монолит.
4. **Нет нужных ролей.** 35 человек без SRE (эксплуатация распределённых систем), технического
   писателя и BA (анализ домена).
5. **Непрерывность бизнеса обязательна.** Платформу нельзя останавливать: единовременная замена
   (big-bang) означает простой — штрафы DSP и потеря клиентов. Кроме того, систему нельзя переписать
   полностью — допустима только постепенная миграция.
6. **Распределённые сложности появляются сразу** — сеть, согласованность данных, отладка, — при том что
   команда не имеет такого опыта.

Принцип: архитектурный стиль выбирается для модуля, а не для всей системы сразу.

### 1.3 Выбранный подход: Strangler Fig

**Суть:** новый функционал выносится в отдельные сервисы, а старый монолит постепенно «замещается»
за фасадом API Gateway. Монолит остаётся работоспособным до полного переключения — в отличие от
единовременной замены.

**Механизмы безопасного переключения:**
- **Feature flag** (переключатель функции) — трафик направляется в новый сервис или в монолит по флагу, без релиза;
- **Canary** (канареечный выпуск) — сначала малая доля трафика (например, 1–5%), затем увеличение;
- **Shadow-трафик** (теневой) — запросы дублируются в новый сервис, ответы сравниваются, но клиенту не отдаются.

**Почему именно Strangler Fig:**

| Подход | Суть | Ограничение для AdScale |
|---|---|---|
| Модульный монолит | Границы модулей внутри одного приложения | Не решает SLA и время отклика: один процесс и одна БД; не даёт выйти на 50 000 RPS |
| Постепенная декомпозиция | Выделение сервисов по доменам | Нет фасада → рискованное переключение, сложнее откат, выше риск простоя |
| **Strangler Fig (выбран)** | Фасад + постепенное замещение | Позволяет откат на каждом шаге и сохраняет непрерывность бизнеса |

**Порядок выноса — по величине влияния на SLA и с учётом 3-месячного срока:**

*Этап 1 (3 месяца, промежуточное решение):*
1. **API Gateway** — единая точка входа для DSP: аутентификация, ограничение частоты, маршрутизация.
2. **Bidding Service** — критический путь, определяет P95 и риск штрафов DSP.
3. **Statistics Service** — снять прямую запись из синхронного пути (Kafka), конкуренция с транзакциями.
4. **Analytics Service** — перевести чтение на read replica PostgreSQL, убрать тяжёлые запросы с production.

*Этап 2 (4–9 месяцев):*
5. **Kubernetes** — оркестрация и автоматическое масштабирование.
6. **ClickHouse** — перенос событий и аналитики в отдельное хранилище.
7. **Financial Service** — изоляция денег и идемпотентности.
8. **Campaign Service**, **Delivery Service** — по мере готовности.

*Целевое состояние (год):* service mesh, мультирегион.

Каждый шаг обратим: при деградации трафик возвращается в монолит флагом.

**Обоснование:** стратегия эволюции и выбор Strangler Fig — в `adr/ADR-001-evolution-strategy.md`;
приоритет сервиса ставок как первого шага — в `adr/ADR-002-bidding-first.md`.

**Analytics Service** (сервис аналитики) · **Financial Service** (финансовый сервис).

## 3. Доменные сервисы и обоснование границ (DDD)

Границы — по бизнес-семантике (DDD, Bounded Context — ограниченный контекст), а не по техническим слоям.
Каждый доменный контекст соответствует контейнеру C4.

| Bounded Context | Сервис | Ответственность | Почему граница |
|---|---|---|---|
| Ставки / аукцион | **Bidding Service** (сервис ставок) | Приём bid-request, аукцион, победитель, bid-response | Критический путь, чувствителен к задержкам; изолировать от аналитики и статистики |
| Кампании | **Campaign Service** (сервис кампаний) | Кампании, бюджетные лимиты, ставки, таргетинг | Преимущественно чтение, кешируемо; своя модель данных |
| Выдача / креативы | **Delivery Service** (сервис выдачи) | Генерация разметки баннера, creative | Отдельная логика рендеринга, не нагружает БД |
| Статистика / события | **Statistics Service** (сервис статистики) | Приём показов и кликов, запись в хранилище | Преимущественно запись, append-only; изолировать от транзакций |
| Аналитика / отчётность | **Analytics Service** (сервис аналитики) | Отчёты и агрегаты | Аналитическая обработка (OLAP — аналитическая обработка запросов), тяжёлые запросы; отдельное хранилище |
| Финансы | **Financial Service** (финансовый сервис) | Списание, счета, балансы | Транзакции (ACID), деньги, идемпотентность |

**Инфраструктурные компоненты (не домены):**
- **API Gateway** — единая точка входа: аутентификация, ограничение частоты, маршрутизация,
  Circuit Breaker, мониторинг времени отклика. Не является доменом — инфраструктурный слой.
- **Dashboard BFF** — слой агрегации данных для UI кабинета рекламодателя. Не является доменом —
  слой представления.

### 3.1 Соответствие AS-IS → TO-BE

Показывает, что каждый компонент текущего монолита учтён в целевой архитектуре.

| Компонент AS-IS | Сервис TO-BE | Что произошло |
|---|---|---|
| Ad Server + Auction Engine | **Bidding Service** | Выделен критический путь (аукцион и ответ DSP) |
| — | **Campaign Service** | Выделен отдельный домен кампаний, бюджетов и таргетинга |
| Delivery Service | **Delivery Service** | Сохранён, выведен из монолита |
| Statistics Service | **Statistics Service** | Вынесен на Kafka + ClickHouse, снята нагрузка с транзакционной БД |
| Financial Service | **Financial Service** | Изолирован, добавлена идемпотентность и сверка |
| Analytics Service | **Analytics Service** | Вынесен на ClickHouse, изолирован от production-БД |
| Advertiser Dashboard | **Dashboard BFF** | Backend кабинета вынесен в отдельный слой; UI обращается к сервисам через BFF |
| — | **API Gateway** | Новая единая точка входа (аутентификация, ограничение частоты, контроль SLA) |

## 4. Взаимодействие

| Пара | Протокол | Почему |
|---|---|---|
| DSP → API Gateway → **Bidding Service** | HTTP / **OpenRTB** | Стандарт RTB, контракт партнёра |
| **Рекламодатель** → API Gateway → **Dashboard BFF** | HTTPS (клиент) / HTTP (внутри) | Управление кампаниями и бюджетами через кабинет |
| **Пользователь** → **Delivery Service** | HTTPS | Запрос рекламы, просмотр и клики |
| **Financial Service** → Платёжный шлюз | HTTPS / REST | Пополнение рекламного бюджета, зачисление средств |
| **Bidding Service** → Redis | Redis | Чтение кампаний, бюджетов и ставок из кеша |
| **Campaign Service** → Redis | Redis | Инициализация счётчика бюджета |
| **Campaign Service** → PostgreSQL | JDBC | Чтение и запись кампаний, таргетинга |
| **Financial Service** → PostgreSQL | JDBC | Транзакции, счета, балансы |
| **Bidding Service** → **Campaign Service** | **gRPC** | Низкое время отклика, строгий контракт; при промахе кеша — запрос в Campaign |
| **Bidding Service** → **Campaign Service** (переходный период) | REST / ACL (слой-переходник) | Пока Campaign в монолите — чтение кампаний через API монолита |
| **Bidding Service** → **Delivery Service** | gRPC / Internal Call | Низкое время отклика |
| **Delivery Service** → Kafka | **асинхронно** | События показов и кликов, буферизация, развязка |
| **Campaign Service** → Kafka → **Bidding Service** | **асинхронно** | Событие `campaign.updated` — инвалидация кеша |
| **Bidding Service** → Kafka | **асинхронно** | События ставок, результаты аукционов, списания |
| Kafka → **Statistics Service** | **асинхронно** | Потребление событий показов, кликов и ставок |
| Kafka → **Analytics Service** | **асинхронно** | Потребление событий для расчёта агрегатов |
| Kafka → **Financial Service** | **асинхронно** | События списаний для проводок и сверки |
| **Statistics Service** → PostgreSQL (этап 1) | **JDBC** | Партиционированные таблицы событий |
| **Statistics Service** → ClickHouse (этап 2) | асинхронно / пакетно | Высокая нагрузка на запись, append-only |
| **Analytics Service** → Read replica (этап 1) | **JDBC** | Аналитические запросы в обход мастера |
| **Analytics Service** → ClickHouse (этап 2) | SQL (асинхронно) | Аналитическая обработка, не нагружает транзакционную БД |
| **Dashboard BFF** → **Campaign Service**, **Financial Service**, **Analytics Service** | REST | Клиентский слой, агрегация данных для UI |
| **Financial Service** ↔ **Bidding Service** | асинхронно (Kafka) + идемпотентный API | Списания; согласование через события + сверка |

**Обоснование:**
- **gRPC** для «Bidding Service ↔ Campaign Service» — бинарный формат и HTTP/2 дают меньше накладных
  расходов и строгий контракт; важно для SLA.
- **Kafka** для событий — высокая пропускная способность, хранение и повторное чтение (replay),
  развязка производителей и потребителей, надёжная доставка.
- **REST** — для клиентских и партнёрских API, где важен простой контракт.

**Нужен ли API Gateway:** да. Единая точка входа для DSP и клиентов: аутентификация, ограничение
частоты, маршрутизация, Circuit Breaker и измерение времени отклика (требование SLA к DSP).

**Почему показ рекламы идёт напрямую в Delivery Service:** трафик публичный, аутентификация не требуется,
а объём показов выше потока bid-request — нагружать им общий API Gateway нецелесообразно.
Вход обеспечивается балансировщиком/CDN.

## 5. Инфраструктура

| Компонент | Назначение | Зачем в AdScale |
|---|---|---|
| **Балансировщик нагрузки** (L4/L7) | Распределение входящего трафика между экземплярами API Gateway | Убирает API Gateway как единую точку отказа, держит рост до 50 000 RPS |
| **API Gateway** (Envoy) | Единая точка входа: аутентификация (mTLS / API key), ограничение частоты, маршрутизация, Circuit Breaker, метрики времени отклика | Контроль SLA для DSP, защита от всплесков, измерение времени отклика по входящему трафику |
| **Kafka-кластер** | Брокер событий: показы, клики, события ставок и списаний; DLQ (Dead Letter Queue — очередь необработанных сообщений), группы потребителей, хранение и replay (повторное чтение) | Снимает нагрузку на запись с транзакционной БД, буферизует пики, развязывает производителей и потребителей |
| **Redis Cluster** | Кеш кампаний, бюджетов и ставок; счётчик расхода бюджета | Убирает синхронные обращения к БД на критическом пути; резервирование бюджета до участия в аукционе |
| **PostgreSQL на сервис** (для Campaign и Financial — с read replica) | Транзакционное хранилище **Campaign Service** и **Financial Service** | ACID (атомарность, согласованность, изолированность, долговечность) для денег и кампаний; реплика снимает нагрузку чтения; изоляция данных по сервисам |
| **ClickHouse** | Колоночное хранилище событий и аналитики | Аналитическая нагрузка не конкурирует с транзакционной БД |
| **Kubernetes** | Оркестрация контейнеров: масштабирование, самовосстановление, rollout (выпуск версий) | Горизонтальное масштабирование сервисов и безопасный выпуск версий |
| **CI/CD и реестр образов** | Сборка, тесты, публикация образов, автоматический деплой | Быстрый и безопасный выпуск; ручной деплой — ограничение из ТЗ |
| **Хранилище секретов и конфигурации** (Vault / Kubernetes Secrets) | Ключи API, сертификаты mTLS, параметры окружения | Безопасность партнёрских интеграций; конфигурация вне кода (12-factor) |
| **Наблюдаемость**: Prometheus + Grafana, OpenTelemetry + Jaeger, ELK/Loki | Метрики, трассировка, логи | Диагностика деградаций и контроль SLA |
| **Service Mesh (Istio)** | mTLS (взаимная аутентификация) между сервисами, сетевые политики, retry только для идемпотентных вызовов (не для `bid-request`) | Только этап зрелости (год): на старте достаточно API Gateway и Circuit Breaker в сервисах |

## 6. Данные (Database per Service — своя БД у каждого сервиса)

| Сервис | Хранилище | Обоснование |
|---|---|---|
| **Bidding Service** (сервис ставок) | Redis (кеш) + Kafka (публикация событий) | **Без собственного состояния (stateless):** состояние аукциона живёт только в рамках запроса и не сохраняется. Данные получает из кеша Redis и Campaign Service; результаты публикует в Kafka. Собственная БД не нужна — это осознанное решение ради времени отклика |
| **Campaign Service** (сервис кампаний) | PostgreSQL (master + read replica); Redis — кеш | Транзакционные данные, преимущественно чтение, кешируемо |
| **Statistics Service** (сервис статистики) | PostgreSQL с партиционированием (этап 1) → ClickHouse (этап 2) | Высокая нагрузка на запись, append-only, колоночное хранилище |
| **Analytics Service** (сервис аналитики) | ClickHouse (этап 2); на этапе 1 — read replica PostgreSQL | OLAP, тяжёлые агрегаты, изоляция от транзакций |
| **Financial Service** (финансовый сервис) | PostgreSQL (master + read replica, ACID) | Транзакции, деньги, идемпотентность; реплика — для отчётов и сверки |
| **Delivery Service** (сервис выдачи) | Без собственной БД (stateless) | Только формирует разметку по данным аукциона; состояние не хранит |
| **API Gateway**, **Dashboard BFF** | Без собственной БД | Маршрутизация и агрегация; данные получают через API сервисов |

Подробно — `Task3/database-strategy.md`.

### 6.1 Владение данными и миграция

| Данные | Текущее место | Новый владелец |
|---|---|---|
| Кампании, бюджетные лимиты, ставки (bid-настройки), таргетинг | Общая PostgreSQL | **Campaign Service** |
| Bid-запросы и ответы (bid-request / bid-response) | Не хранятся | **Не хранятся** (эфемерны, живут в рамках запроса); фиксируются только события в Kafka |
| Результаты аукционов | Общая PostgreSQL | **Kafka** (журнал событий) → **Statistics Service** (ClickHouse, отчётность), **Financial Service** (списания) |
| События показов и кликов | Общая PostgreSQL | **Statistics Service** → ClickHouse |
| Финансы, счета, балансы | Общая PostgreSQL | **Financial Service** |
| Аналитические агрегаты | Общая PostgreSQL (расчёт по запросу) | **Analytics Service** → ClickHouse |

**Механизм перехода (без простоя):**
1. **CDC** (Change Data Capture — захват изменений из журнала БД) — перенос снимка данных и
   непрерывная синхронизация изменений из старой схемы.
2. **Dual-write** — на переходный период запись идёт и в старую схему, и в новый сервис.
3. **Переключение чтения** на новый сервис (canary — сначала доля трафика, затем полный).
4. **Отключение** старой схемы после периода стабильной работы.

Согласованность между БД — через события Kafka и сверку (reconciliation); распределённые операции —
Saga (см. `Task2/reliability.md`).

## 7. Бюджет времени отклика (критический путь, ≤80/100 мс)

Бюджет рассчитан на **P95** и распределён по этапам bid-request.

| # | Этап | Попадание в кеш | Промах кеша |
|---|---|---|---|
| 1 | Сеть: DSP → балансировщик → API Gateway | ~3 мс | ~3 мс |
| 2 | **API Gateway**: аутентификация, маршрутизация, Circuit Breaker | ~5 мс | ~5 мс |
| 3 | **Bidding Service**: разбор OpenRTB | ~8 мс | ~8 мс |
| 4 | **Bidding Service**: аукцион в памяти | ~20 мс | ~20 мс |
| 5 | **Redis**: кампании, бюджеты, ставки | ~2 мс | ~2 мс |
| 6 | **Campaign Service** (только при промахе) | — | ~10 мс |
| 7 | **Delivery Service**: разметка | ~5 мс | ~5 мс |
| 8 | Сеть: Gateway → DSP | ~3 мс | ~3 мс |
| | **Итого** | **~46 мс** | **~56 мс** |
| | **Запас до 80 мс (DSP)** | **~34 мс** | **~24 мс** |

На критическом пути нет JDBC-запросов — только Redis и вызовы Campaign (REST через ACL
на этапе 1, gRPC на этапе 2) и Delivery (gRPC). Асинхронные потоки (Kafka, ClickHouse,
статистика, финансы) в бюджет не входят и на время ответа DSP не влияют.

Механизмы надёжности (Circuit Breaker, Retry с экспоненциальной задержкой, идемпотентность,
резервные стратегии, Saga) описаны в `Task2/reliability.md`.

## 8. Эволюция

### 8.1 Промежуточное решение (3 месяца, 18 000 RPS, P95 ≤100 мс)

**Цель:** подключить DSP без деградации SLA, удержать клиентов, обеспечить ≥18 000 RPS,
P95 ≤100 мс, стабильную работу сервиса ставок, масштабируемость горячих компонентов
и разделение критичных и некритичных потоков.

**Состав работ:**

| # | Работа | Результат |
|---|---|---|
| 1 | **API Gateway** (аутентификация, ограничение частоты, маршрутизация, Circuit Breaker), 2+ экземпляра за балансировщиком | DSP подключён, трафик под контролем, нет единой точки отказа |
| 2 | **Bidding Service** + Redis + ACL: вынос критического пути, кеш кампаний и бюджетов, чтение из монолита через слой-переходник, shadow → постепенное переключение; **Circuit Breaker, таймауты, fallback (no-bid)** | P95 ≤100 мс, независимое горизонтальное масштабирование, отсутствие сбоев сервиса ставок |
| 3 | **Redis с репликацией** + счётчик расхода бюджета | Кеш для SLA; бюджет не превышается |
| 4 | **Асинхронная обработка статистики**: **Statistics Service** как потребитель Kafka — события вне синхронного пути → **Kafka (один брокер, JSON-схема)** → запись в PostgreSQL с партиционированием | Запись событий не влияет на критический путь |
| 5 | **Read replica PostgreSQL** для аналитики | Тяжёлые запросы не блокируют production |
| 6 | **Docker и автоматический деплой** | Сервис ставок ставится в прод без ручных операций |
| 7 | **Метрики и логи**, разделение ресурсов критичного и некритичных потоков | Контроль SLA и диагностика |

**Команда и срок:** выделенные 6 backend, 2 DevOps, 2 тестировщика (остальные поддерживают
текущий продакшен). 9–10 недель работы + 2–3 недели на shadow-прогон и регрессию — **11–13 недель**
(в пределах 3 месяцев).

**Допущения:** ACL — read-only API монолита без изменения бизнес-логики; монолит продолжает
обслуживать остальные потоки (кампании, кабинет, финансы); нагрузочный тест на 18 000 RPS
проводится до переключения трафика.

Схема промежуточного состояния: `diagrams/c4-container-interim.puml`.

**Почему не модульный монолит на этом этапе.** Модульный монолит проще и дешевле, но не позволяет
масштабировать сервис ставок независимо (масштабируется весь процесс) и не разделяет критичный
и некритичные потоки по ресурсам. Кеш и Kafka применимы и внутри монолита, но без выноса Bidding
нельзя гарантировать изоляцию критического пути; требование «наиболее нагруженные компоненты
масштабируются» остаётся невыполненным.

### 8.2 Этап 2 (4–9 месяцев)

| Работа | Что усиливаем относительно этапа 1 |
|---|---|
| **ClickHouse** | События и аналитика переезжают из партиционированных таблиц PostgreSQL в колоночное хранилище |
| **Financial Service** | Изоляция, идемпотентность, сверка |
| **Kubernetes** | Оркестрация и автоматическое масштабирование вместо Docker + скрипта деплоя |
| **Полный CI/CD** | Тесты, staging, автоматический rollback |
| **Распределённая трассировка** | OpenTelemetry + Jaeger вместо метрик и логов |
| **Kafka-кластер** | Несколько брокеров, Schema Registry, Avro вместо одного брокера и JSON |
| **Redis Cluster** | Кластер вместо одного инстанса с репликой |
| **Campaign Service, Delivery Service** | Вынос из монолита |
| **Service mesh** | При переходе к целевому состоянию (после этапа 2) |

### 8.3 Целевое решение (год, 50 000 RPS, SLA 99.9%)
- Все сервисы выделены, событийно-ориентированная обработка.
- Горизонтальное масштабирование, Kubernetes.
- Мультирегиональное развёртывание, service mesh, высокая доступность (HA).
- Kafka-кластер с репликацией между регионами.
- Мультиплатформенная интеграция.

## 9. Итог

Целевая архитектура снимает ключевое противоречие: атрибуты качества (P95 ≤100 мс, 18 000 → 50 000 RPS,
SLA 99.9%) против текущего монолита на одной БД.

| Драйвер | Как решено |
|---|---|
| **Performance** (P95 ≤100 мс, DSP ≤80) | Критический путь без синхронной БД: Redis + gRPC; бюджет ~46–56 мс |
| **Scalability** (18 000 → 50 000 RPS) | Stateless Bidding, горизонтальное масштабирование, Database per Service |
| **Availability** (SLA 99.9%) | Устранены точки отказа: репликация, 2+ экземпляра Gateway, Redis с репликой; мультирегион — на году |
| **Reliability** | Circuit Breaker, таймауты, идемпотентность, резервирование бюджета, Saga |
| **Modifiability** | Strangler Fig, независимая поставка сервисов |
| **Security** | mTLS / API key, хранилище секретов |
| **Maintainability** | Метрики, логи, распределённая трассировка |

**Результат по этапам:**
- **3 месяца:** DSP подключён, 18 000 RPS, P95 ≤100 мс, критичные и некритичные потоки разделены.
- **Год:** 50 000 RPS, мультирегиональное развёртывание, SLA 99.9%.

Переход эволюционный (Strangler Fig) — непрерывность бизнеса сохраняется на каждом шаге.

Обоснование ключевых решений — в ADR: `ADR-001` (стратегия эволюции), `ADR-002` (сервис ставок первым),
`ADR-003` (Kafka).
