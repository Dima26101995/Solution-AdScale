## Краткое резюме

**AS-IS.** Монолит, одна PostgreSQL, без кеша, очередей и контейнеризации. 15 000 RPS,
P95 110–120 мс при норме ≤100 мс, деградации в часы пик. Главные проблемы: синхронные обращения
к БД в пути обработки bid-request, неразделённые критичные и некритичные потоки, единственная БД
как точка отказа (SPOF — Single Point of Failure), нет горизонтального масштабирования.

**TO-BE.** Доменные сервисы (Bidding Service, Campaign Service, Delivery Service, Statistics Service,
Analytics Service, Financial Service) и инфраструктурные компоненты (API Gateway, Dashboard BFF);
Kafka для событий, Redis для кеша и учёта расхода бюджета, PostgreSQL на сервис, ClickHouse для аналитики.
Критический путь без синхронной БД, бюджет времени отклика по шагам.
Целевые показатели: **18 000 RPS (3 мес) → 50 000 RPS (год), SLA 99.9%**.
Механизмы надёжности (Circuit Breaker, Retry, идемпотентность, Saga) вынесены в Task 2.

**Стратегия.** Strangler Fig (постепенное вырезание из монолита).
К 3 месяцам: API Gateway, сервис ставок + Redis + ACL, Kafka для статистики, read replica для аналитики,
Docker и автоматический деплой, наблюдаемость.
Этап 2 (4–9 месяцев): ClickHouse, изоляция финансов, Kubernetes, вынос кампаний и выдачи.
Непрерывность бизнеса сохраняется на каждом шаге.

## Ключевые решения

- **ADR-001** — Strangler Fig (а не полная переработка и не «оставить монолит»).
- **ADR-002** — сервис ставок выделяем первым (критический путь, SLA).
- **ADR-003** — Kafka для потоковой обработки событий.
