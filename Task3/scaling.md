# Масштабирование

Документ раскрывает **пункт 2** задания: репликация, шардирование, read replicas, CQRS.

Профиль нагрузки: 15 000 → 18 000 (3 месяца) → 50 000 RPS (год). Нагрузка регулярная,
пики — в часы показов.

## 1. Для каких сервисов репликация master-slave

| Сервис | Почему |
|---|---|
| Campaign Service | Чтений больше, чем записи: каталог, отчёты, аналитика |
| Financial Service | Критичность данных и доступность; RPO 0 |
| Redis | Кеш и счётчик: чтение с реплики, переживание отказа узла |

**Не применяется:** Bidding (нет БД), Statistics (пишет партиями), Analytics (читает
read replica и CQRS).

Тип — master-slave, не multi-master: запись централизована, multi-master нужен для
нескольких ЦОД — это год. Campaign — асинхронная репликация (RPO 5 минут),
Financial — синхронная (RPO 0). Контроль lag; при превышении порога чтение — с мастера.

## 2. Что и по какому ключу шардировать

| Данные | Ключ | Почему |
|---|---|---|
| События показов и кликов | Дата и час | Диапазонные запросы, старые партиции удаляются |
| Кампании и лимиты | `campaign_id` | Все данные кампании на одном шарде |
| Финансы | `campaign_id` | Тот же ключ — проще сверка |

На этапе 1 шардирование не применяется: 18 000 RPS выдерживает PostgreSQL с репликой.
На году — шардирование по `campaign_id`.

## 3. Нужны ли read replicas для сервиса аналитики

**Да, обязательны.** Тяжёлые агрегаты не должны конкурировать с записью и ронять SLA.

Analytics читает read replica Campaign на этапе 1, ClickHouse — на этапе 2.
Правило: запись — только в мастер, чтение — с реплики; «прочитал сразу после записи» —
с мастера. Dashboard BFF читает через API сервисов, не из реплики.

## 4. Где применимо CQRS

| Поток | Запись | Чтение |
|---|---|---|
| Статистика | Kafka → PostgreSQL (этап 1) / ClickHouse (этап 2) | Analytics, Dashboard |
| Кампании | Мастер PostgreSQL | Redis-кеш + read replica |
| Финансы | Мастер PostgreSQL | Реплика: отчёты, сверка |

Для Bidding не применяется: у него только чтение кеша.

## 5. Горизонтальное масштабирование сервисов

| Сервис | Как масштабируется | Ограничение |
|---|---|---|
| Bidding Service | 2+ stateless-экземпляра за балансировщиком | Нет — состояние в Redis |
| API Gateway | 2+ экземпляра | Нет |
| Dashboard BFF | 2+ экземпляра | Нет |
| Delivery Service | 2+ экземпляра | Нет |
| Campaign Service | 2+ экземпляра; запись — в мастер | Запись идёт в мастер |
| Statistics Service | 2+ потребителя Kafka (группа) | Число партиций Kafka |
| Analytics Service | 2+ экземпляра | Тяжёлые запросы |
| Financial Service | 2+ экземпляра; запись — в мастер | Деньги: только мастер |

Вертикальное масштабирование — временная мера для мастера PostgreSQL.

## 6. Автоматическое масштабирование

| Этап | Механизм |
|---|---|
| Этап 1 (3 месяца) | Вручную: 2+ экземпляра, Docker |
| Этап 2 (4–9 месяцев) | Kubernetes HPA: по CPU и RPS |
| Целевое (год) | Мультирегион, автоматическое переключение трафика |

## 7. Что ограничивает рост

| Ограничение | Решение |
|---|---|
| Мастер PostgreSQL по записи | Шардирование по `campaign_id` (год) |
| Число партиций Kafka | Увеличить партиции и потребителей |
| Один инстанс Redis | Redis Cluster (этап 2) |
| Один production-кластер | Мультирегион (год) |
| Нет SRE | Runbook, автодеплой, метрики |
