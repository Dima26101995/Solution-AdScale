# Потоковая обработка событий

Документ раскрывает **пункт 4** (потоковая обработка данных) задания.

**Этапы:** этап 1 — первые 3 месяца; этап 2 — 4–9 месяцев (см. `TO-BE` 8).

## 1. Назначение

Kafka развязывает производителей и потребителей: запись событий не блокирует ответ DSP,
пики сглаживаются, а Statistics, Financial и Analytics читают свои потоки независимо.

## 2. Топики

| Топик | Событие | Продюсер | Потребители | Ключ | Retention |
|---|---|---|---|---|---|
| `impression.events` | Показ рекламы | Delivery | Statistics, Analytics | `campaign_id` | 7 дней |
| `click.events` | Клик по рекламе | Delivery | Statistics, Analytics | `campaign_id` | 7 дней |
| `bid.events` | Результат аукциона | Bidding | Statistics | `campaign_id` | 7 дней |
| `billing.events` | Списание, резервирование | Bidding | Financial | `campaign_id` | 30 дней |
| `campaign.updated` | Изменение кампании | Campaign | Bidding (инвалидация кеша) | `campaign_id` | 1 день |

`billing.events` хранится дольше: по нему проводится сверка и разбор расхождений.

## 3. Партиционирование

| Параметр | Значение |
|---|---|
| Ключ партиции | `campaign_id` |
| Порядок | Гарантируется в пределах партиции — события одной кампании не перемешиваются |
| Число партиций | По числу потребителей с запасом (этап 1 — 6, этап 2 — больше) |
| Брокеры | Этап 1 — 1 брокер; этап 2 — 3 брокера с репликацией партиций |

Ключ по `campaign_id`, а не по `user_id`: все события кампании должны обрабатываться
по порядку, чтобы статистика и списания сходились.

## 4. Схемы событий

| Этап | Формат | Почему |
|---|---|---|
| Этап 1 (3 месяца) | JSON | Проще стартовать, читаемо, достаточно для объёмов |
| Этап 2 (4–9 месяцев) | Avro + Schema Registry | Компактнее, строгая схема, контроль совместимости |

Переход на Avro — без остановки: новый формат публикуется в новый топик, потребители
переключаются постепенно.

## 5. Группы потребителей

| Группа | Сервис | Что делает |
|---|---|---|
| `statistics` | Statistics Service | Пишет события в PostgreSQL (этап 1) / ClickHouse (этап 2) |
| `financial` | Financial Service | Списания, сверка |
| `analytics` | Analytics Service | Агрегаты и отчёты |
| `cache-invalidation` | Bidding Service | Инвалидация кеша по `campaign.updated` |

Группа даёт параллельную обработку: несколько экземпляров сервиса делят партиции.

## 6. Гарантии

| Параметр | Значение |
|---|---|
| Доставка | Не менее одного раза: событие не теряется, но может прийти повторно |
| Дедупликация | По `event_id` у потребителя |
| Порядок | В пределах партиции по `campaign_id` |
| Подтверждение | Продюсер ждёт подтверждения записи (acks=all) |
| Кворум реплик | Этап 1 — 1 (один брокер); этап 2 — 2 из 3 для `billing.events` |
| Идемпотентный продюсер | Включён — защита от дублей при повторной отправке |

## 7. Ошибки и DLQ

| Ситуация | Действие |
|---|---|
| Временная ошибка потребителя | 3 попытки с экспоненциальной паузой |
| Постоянная ошибка (битые данные) | Сообщение уходит в DLQ (`*.dlq`) |
| Сообщение в DLQ | Алерт дежурному, ручной разбор, повторная публикация |

DLQ не даёт «отравленному» сообщению блокировать партицию.
