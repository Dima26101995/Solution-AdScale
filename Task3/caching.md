# Кэширование

Документ раскрывает **пункт 3** (кеширование) задания.

## 1. Что кэшируем

| Данные | Где | Зачем |
|---|---|---|
| Кампании и таргетинг | Redis | Убрать синхронную БД с критического пути |
| Ставки и лимиты | Redis | Ответ аукциона без запроса в Campaign |
| Счётчик доступного бюджета | Redis | Атомарная проверка и резерв |
| Список кампаний по срезу (гео, устройство, формат) | Redis | Быстрый подбор кандидатов |

Кэшируем только то, что часто читается и редко меняется. Деньги кэшируются как счётчик,
а не как баланс: источник истины — Financial Service.

## 2. Кеш на уровне приложения

Локальный (в памяти процесса) кеш Bidding — для данных, нужных на каждом аукционе.

| Данные | TTL | Инвалидация |
|---|---|---|
| Справочники (гео, устройства, форматы) | 1 час | По версии справочника из ответа Campaign |
| Конфигурация (таймауты, пороги) | 1 час | Перезапуск или сигнал |

Почему так мало: экземпляров Bidding несколько, локальный кеш у каждого свой — данные
расходятся. В памяти держим только «медленные» данные, а кампании, ставки и бюджет —
в Redis, где все экземпляры видят одно состояние.

## 3. Паттерн Cache-Aside

1. Сервис ищет данные в Redis.
2. При промахе обращается в Campaign Service.
3. Кладёт результат в Redis с TTL.
4. Возвращает ответ.

При изменении кампании кеш не обновляется, а **удаляется** — следующий запрос заполнит
его свежими данными.

## 4. Redis

**Размещение:** в той же зоне доступности, что и сервис ставок — минимальная сетевая
задержка; отдельно от PostgreSQL, чтобы кеш не конкурировал с транзакциями за ресурсы.

| Этап | Конфигурация | Зачем |
|---|---|---|
| Этап 1 (3 месяца) | 1 инстанс + реплика | Кеш и счётчик; реплика — на чтение и на случай отказа |
| Этап 2 (4–9 месяцев) | Redis Cluster (3 сегмента, каждый с репликой) | Горизонтальное масштабирование, отказоустойчивость |

Redis не является источником истины: при полной потере кеш восстанавливается из
Campaign Service, бюджет — сверкой с Financial.

## 5. TTL

| Данные | TTL | Почему |
|---|---|---|
| Кампании и таргетинг | 5 минут | Компромисс: свежесть против нагрузки на Campaign |
| Список кандидатов по срезу | 5 минут | Тот же срез |
| Счётчик бюджета | До конца периода кампании | Не должен сбрасываться |
| Резерв бюджета | 60 секунд | Временная запись, затем компенсация |

Правило: чем быстрее устаревают данные, тем короче TTL. Для кампаний 5 минут — потому что
изменения приходят событием и инвалидируются сразу, а TTL страхует от потери события.

## 6. Инвалидация

| Стратегия | Где | Когда |
|---|---|---|
| По событию | `campaign.updated` → Cache Invalidator | Кампания изменена — ключи удаляются сразу |
| По TTL | Все ключи | Страховка, если событие потеряно |
| По версии | Не используется | Избыточно при текущем объёме |

Комбинация «событие + TTL»: событие даёт точность, TTL — устойчивость к сбою Kafka.

## 7. Прогрев

| Когда | Что | Как |
|---|---|---|
| При деплое / рестарте | Кампании активных рекламодателей | Warming job Bidding читает из Campaign порциями |
| Перед пиком | Топ кампаний по показам | По расписанию |
| После инвалидации | Затронутые ключи | Ленивое заполнение при первом запросе |

Правила прогрева:
- загружать батчами с ограничением скорости, чтобы не перегрузить Campaign;
- не греть всё подряд — только активные кампании;
- прогрев не должен сам стать причиной деградации.
