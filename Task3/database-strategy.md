# Стратегия работы с данными (Database per Service)

Документ раскрывает **пункт 1** (Database per Service) задания.
Отказоустойчивость данных (пункт 5) — в [`failover.md`](failover.md).

## 1. Принцип

Каждый сервис владеет своими данными и не читает таблицы другого сервиса напрямую.
Обмен — через API или события. Это убирает общую схему, из-за которой в монолите изменение
одной таблицы ломало отчёты и другие модули.

## 2. Выбор базы данных для каждого сервиса

| Сервис | Тип базы данных | Обоснование |
|---|---|---|
| **Сервис ставок** (Bidding Service) | **Своей БД нет** (stateless); Redis — кеш, Kafka — события | Состояние живёт в рамках запроса. Нужны миллисекунды — синхронная БД недопустима |
| **Сервис кампаний** (Campaign Service) | PostgreSQL (master + read replica); Redis — кеш | Транзакционные данные, преимущественно чтение, кешируемо |
| **Сервис статистики** (Statistics Service) | PostgreSQL с партиционированием (этап 1) → ClickHouse (этап 2) | Высокая нагрузка на запись, append-only |
| **Сервис аналитики** (Analytics Service) | ClickHouse (этап 2); на этапе 1 — read replica PostgreSQL | Тяжёлые агрегаты не должны конкурировать с транзакциями |
| **Сервис финансов** (Financial Service) | PostgreSQL (master + read replica) | Деньги: ACID, идемпотентность, сверка; реплика — для отчётов |

**Без собственной БД:** Delivery Service (только разметка), API Gateway и Dashboard BFF
(маршрутизация и агрегация).

## 3. Почему не одна БД

| Проблема общей БД | Следствие в AdScale |
|---|---|
| Запись событий конкурирует с транзакциями | Рост времени отклика в часы пик |
| Аналитика блокирует таблицы | Деградация аукциона |
| Изменение схемы ломает чужие модули | Медленные и рискованные релизы |
| Нельзя масштабировать хранилище под конкретный профиль | Один инстанс на всё |

## 4. Что не делаем на этапе 1

- **Шардирование** — 18 000 RPS выдерживает PostgreSQL с репликой.
- **Event sourcing** — журнал в Kafka уже даёт историю.
- **Своя БД для сервиса ставок** — stateless, БД ухудшит время отклика.
