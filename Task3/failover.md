# Отказоустойчивость данных (failover)

Документ раскрывает **пункт 5** (отказоустойчивость данных) задания.

## 1. RPO и RTO

**RPO** (Recovery Point Objective) — сколько данных допустимо потерять.
**RTO** (Recovery Time Objective) — за сколько система должна восстановиться.

| Сервис | Данные | RPO | RTO | Обоснование |
|---|---|---|---|---|
| Финансовый сервис | Деньги, балансы | 0 | 15 мин | Потеря и двойное списание недопустимы |
| Сервис кампаний | Кампании, лимиты | 5 мин | 30 мин | Восстанавливается из бэкапа, кеш перезаполнится |
| Сервис статистики | События | 0 (из Kafka) | 1 ч | События можно переиграть |
| Сервис аналитики | Агрегаты | 1 ч | 4 ч | Считаются заново из событий |
| Сервис ставок | Нет своих данных | — | 1 мин | Stateless: поднимается новый экземпляр |
| Delivery | Нет своих данных | — | 1 мин | Stateless: поднимается заново |
| API Gateway | Нет своих данных | — | 1 мин | Stateless: конфигурация в репозитории |
| Dashboard BFF | Нет своих данных | — | 1 мин | Stateless: поднимается заново |

## 2. Резервное копирование

| Хранилище | Механизм | Частота | Хранение |
|---|---|---|---|
| PostgreSQL (финансы) | Непрерывная архивация WAL + база | Непрерывно + ежедневно | 30 дней |
| PostgreSQL (кампании) | Ежедневный бэкап + WAL | Ежедневно | 14 дней |
| PostgreSQL (статистика) | Партиционированные таблицы | — | Не требуется: события переигрываются из Kafka |
| Redis | Снимки RDB + AOF | Каждые 15 минут | 3 дня |
| ClickHouse | Бэкап партиций | Ежедневно | 30 дней |
| Kafka | Retention топиков | — | 7–30 дней |

**Восстановление на момент времени (PITR)** — для PostgreSQL: откат к любой точке
в пределах окна хранения WAL. Для финансов обязательно.

## 3. Сценарии отказов

| Отказ | Поведение | Восстановление |
|---|---|---|
| Экземпляр сервиса ставок упал | Балансировщик убирает его из пула | Новый экземпляр за 1 мин |
| Мастер PostgreSQL недоступен | Запись останавливается, чтение — с реплики | Реплика повышается (этап 1 — runbook, этап 2 — автоматически) |
| Redis недоступен | no-bid: бюджет неизвестен | Кеш прогревается, бюджет сверяется |
| Kafka недоступен | События буферизуются в памяти продюсеров (Bidding, Delivery) | Публикация возобновляется |
| Кампании недоступны | Работа по кешу, затем дефолтная ставка | Кеш и связь восстанавливаются |
| Отказ ЦОД (год) | Переключение на второй регион | Мультирегион, полный failover |

## 4. 12-factor (применимость)

| Фактор | Как в AdScale |
|---|---|
| Кодовая база | Один репозиторий решения; каждый сервис — отдельный модуль со своей сборкой |
| Зависимости | Явно в манифестах, ставятся при сборке образа |
| Конфигурация | Переменные окружения и Vault, не в коде |
| Сторонние службы | PostgreSQL, Redis, Kafka — подключаемые ресурсы |
| Сборка / выпуск / запуск | Разделены: CI → образ → деплой |
| Процессы | Stateless: Bidding и Delivery не хранят состояние |
| Привязка портов | Порт из окружения |
| Параллелизм | Масштабирование экземплярами |
| Устойчивость к сбоям | Graceful shutdown, drain 30 с |
| Сходство сред | Один образ для dev/staging/prod |
| Логи | Поток в stdout, сбор централизованно |
| Административные процессы | Миграции и warming job — отдельные задачи |
