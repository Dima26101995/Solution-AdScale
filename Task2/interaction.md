# Взаимодействие сервисов

## 1. Участники

| Участник | Роль | Протокол |
|---|---|---|
| DSP-партнёр | Внешняя площадка, присылает `bid-request` | OpenRTB / HTTPS |
| API Gateway | Единая точка входа для внешнего трафика | HTTPS снаружи, HTTP внутрь |
| Bidding Service | Аукцион, ответ | HTTP (вход); REST (этап 1) / gRPC (этап 2) |
| Campaign Service | Кампании и таргетинг | REST через ACL (этап 1) / gRPC (этап 2) |
| Delivery Service | Разметка креатива | Internal Call (gRPC) |
| Dashboard BFF | Агрегация данных для UI рекламодателя | REST к сервисам |
| Statistics Service | Потребитель событий | Kafka |
| Analytics Service | Потребитель событий, отчёты | Kafka, read replica |
| Financial Service | Списания и сверка | Kafka, REST (сверка) |

## 2. Протоколы и паттерны взаимодействия

### 2.1 Протоколы по типам связей

| Тип связи | Протокол | Почему |
|---|---|---|
| Внешняя, DSP | HTTPS / OpenRTB (JSON) | Отраслевой стандарт, задан партнёром |
| Внутренняя синхронная, критический путь | REST через ACL (этап 1) → gRPC (этап 2) | Нужен ответ до формирования `bid-response` |
| Внутренняя синхронная, UI | REST / JSON | Отладка важнее микросекунд |
| Потоковая, события | Kafka | Развязка по времени и по потребителям |
| Кеш | Redis protocol | Быстрое чтение кампаний и бюджетов |
| Служебная сверка | REST | Сверка резервов и списаний (Financial ↔ Bidding) |

### 2.2 Паттерны взаимодействия

| Паттерн | Где | Назначение |
|---|---|---|
| **Request-response (sync)** | DSP → Bidding, Bidding → Delivery, Dashboard → сервисы | Ответ нужен для `bid-response` или UI |
| **Fire-and-forget** | Bidding → Kafka | Публикация не блокирует ответ |
| **Publish-subscribe** | Kafka → Statistics, Financial, Analytics | Несколько потребителей независимо |
| **Event notification** | `campaign.updated` → Cache Invalidator | Инвалидация кеша без опроса |
| **Cache-aside** | Bidding → Redis → Campaign | Снижение нагрузки на Campaign |
| **Anti-corruption layer (ACL)** | Bidding → монолит (этап 1) | Изоляция от старой модели данных |
| **Idempotent consumer** | Statistics, Financial | Безопасная повторная доставка |

## 3. Внутреннее взаимодействие

### 3.1 Сравнение подходов

| Критерий | REST / JSON | gRPC | Асинхронный (Kafka) |
|---|---|---|---|
| Время отклика | Среднее (текст, парсинг) | **Низкое** (бинарный protobuf) | Не подходит для синхронного ответа |
| Контракт | Слабый (OpenAPI, необязателен) | **Строгий** (protobuf, кодогенерация) | Схема события |
| Стриминг | Нет | **Есть** | Есть |
| Отладка | **Простая** (curl, логи) | Сложнее (нужен grpcurl) | Сложная (трейсинг) |
| Связность | Синхронная | Синхронная | **Слабая** |
| Когда применять | UI, админка, публичные API | Критический путь между сервисами | События, статистика, финансы |

### 3.2 Выбор по каждой связи

| Связь | Протокол | Обоснование |
|---|---|---|
| DSP → API Gateway → Bidding | **HTTPS / OpenRTB (JSON)** | Внешний стандарт, задан партнёром |
| Рекламодатель → API Gateway → Dashboard BFF | **HTTPS (снаружи) / HTTP (внутрь)** | Управление кампаниями через кабинет |
| Пользователь → Delivery | **HTTPS** | Просмотр рекламы и клики |
| Bidding → Redis | **Redis protocol** | Кампании, бюджеты, ставки из кеша |
| Campaign → Redis | **Redis protocol** | Инициализация счётчика бюджета |
| Campaign → PostgreSQL | **JDBC** | Кампании, таргетинг (этап 2) |
| Financial → PostgreSQL | **JDBC** | Транзакции, балансы |
| Financial → Платёжный шлюз | **HTTPS / REST** | Пополнение бюджета |
| Bidding → Campaign (этап 1) | **REST через ACL** | В монолите нет gRPC-сервера; ACL — read-only REST-фасад |
| Bidding → Campaign (этап 2) | **gRPC** | Критический путь: бинарный формат, строгий контракт, таймаут на уровне вызова |
| Bidding → Delivery | **gRPC (Internal Call)** | Короткий вызов на критическом пути, нужен жёсткий таймаут |
| Dashboard BFF → сервисы | **REST** | UI-запросы, отладка важнее микросекунд |
| Bidding → Financial | **Kafka** | Финансы не должны блокировать запрос; списание асинхронное |
| Delivery / Bidding → Statistics | **Kafka** | События показов и кликов, пиковая нагрузка |
| Campaign → Bidding (инвалидация кеша) | **Kafka** | Событие `campaign.updated`, слабая связность |
| Statistics → PostgreSQL (этап 1) | **JDBC** | Партиционированные таблицы событий |
| Statistics → ClickHouse (этап 2) | **Пакетная запись** | Аналитические события, append-only |
| Analytics → Read replica (этап 1) | **JDBC** | Аналитические запросы в обход мастера |
| Analytics → ClickHouse (этап 2) | **SQL** | Отчёты не конкурируют с транзакционной БД |
| Financial ↔ Bidding (сверка) | **REST** | Сверка резервов и списаний по требованию |

**Ключевое правило:** на критическом пути `bid-request` синхронно вызываются только те
сервисы, без ответа которых нельзя сформировать `bid-response` (Campaign, Delivery).
Всё остальное — асинхронно.

## 4. Внешнее взаимодействие — DSP ↔ AdScale

| Параметр | Решение |
|---|---|
| Протокол | **HTTP/1.1 или HTTP/2, JSON** |
| Стандарт | **OpenRTB 2.5** |
| Направление | DSP → AdScale (`bid-request`), AdScale → DSP (`bid-response`) |
| Инициирует | DSP |

**Почему не gRPC:** внешний протокол задаёт DSP-партнёр. OpenRTB — отраслевой стандарт
на JSON; партнёр его уже поддерживает, а gRPC потребовал бы изменений на его стороне.
Для внешней интеграции выбор протокола не наш — он определён рынком.

**Почему не асинхронно:** RTB по определению синхронный — DSP ждёт ответ в пределах `tmax`
(обычно 80–100 мс). Очередь добавила бы задержку и сделала бы аукцион невозможным.

## 5. Потоковая обработка событий

### 5.1 Топики кликов и показов

| Топик | Событие | Продюсер | Ключ | Потребители | Retention |
|---|---|---|---|---|---|
| `impression.events` | Показ рекламы | Delivery | `campaign_id` | Statistics, Analytics | 7 дней |
| `click.events` | Клик по рекламе | Delivery | `campaign_id` | Statistics, Analytics | 7 дней |

### 5.2 Прочие события

Через Kafka также идут события, необходимые другим потокам:

| Событие | Топик | Продюсер → потребитель | Зачем |
|---|---|---|---|
| Результат аукциона | `bid.events` | Bidding → Statistics | Статистика ставок |
| Списание | `billing.events` | Bidding → Financial | Финансы без блокировки ответа |
| Изменение кампании | `campaign.updated` | Campaign → Bidding | Инвалидация кеша |

### 5.3 Гарантии

| Параметр | Значение |
|---|---|
| Доставка | Не менее одного раза: событие не теряется, но может прийти повторно |
| Повторная доставка | Безопасна: у каждого события уникальный идентификатор, повтор не меняет результат |
| Порядок | События одной кампании обрабатываются по порядку |
| Ошибки | После 3 неудачных попыток событие откладывается в очередь ошибок (DLQ) для ручного разбора |
| Формат | JSON на этапе 1; Avro (компактный формат) с реестром схем на этапе 2 |

## 6. Обоснование выбора

### 6.1 Почему gRPC на этапе 2

1. **Время отклика.** Protobuf компактнее JSON в 3–5 раз, парсинг быстрее — на 18 000 RPS
   это заметно.
2. **Строгий контракт.** Изменение схемы ломает сборку, а не продакшен.
3. **Таймауты и отмена.** Срок жизни запроса передаётся по цепочке вызовов: если `tmax` истёк,
   вызов Campaign отменяется, а не продолжает занимать ресурсы.

Тот же подход применяется к связке Bidding → Delivery: короткий вызов с жёстким сроком.

**Почему не REST:** JSON-парсинг и отсутствие строгого контракта на критическом пути
дают лишние миллисекунды и риск рассинхронизации схем. На этапе 1 REST остаётся вынужденной
мерой: в монолите нет gRPC-сервера, а ACL — read-only REST-фасад.

### 6.2 Почему Kafka для событий

| Причина | Пояснение |
|---|---|
| Развязка | Bidding не ждёт Statistics и Financial |
| Буферизация | Пики событий сглаживаются, PostgreSQL не получает залповую запись |
| Множественные потребители | Statistics, Financial и Analytics читают свои топики независимо |
| Повторная обработка | События хранятся, потребитель может перечитать при сбое |
| Порядок | События одной кампании не перемешиваются |

**Почему не прямая запись в PostgreSQL:** именно она была причиной конкуренции записи
с транзакционными запросами и деградации времени отклика.

## 7. API Gateway — нужен ли и какой

**Нужен.** Без него аутентификация дублируется в каждом сервисе, лимит частоты обходится
через разные экземпляры, время отклика собирается по логам сервисов, а новая версия OpenRTB
требует правок в Bidding.

| Причина | Без Gateway | С Gateway |
|---|---|---|
| Аутентификация DSP | В каждом сервисе | В одной точке |
| Ограничение частоты | Нет единого контроля | Лимиты на партнёра |
| Защита от перегрузки | Сервис падает целиком | Circuit Breaker, отсечение |
| Наблюдаемость | По логам сервисов | Метрики, логи, трассировка на входе |
| Смена версии OpenRTB | Правки в сервисе | Управление версиями |

**Какой.** Сравнение реализаций:

| Критерий | NGINX + Lua | Envoy | Spring Cloud Gateway | Облачный Gateway |
|---|---|---|---|---|
| Производительность | Высокая | **Очень высокая** | Средняя (JVM) | Зависит от провайдера |
| Протоколы | HTTP, HTTPS, gRPC | **HTTP/2, gRPC, TCP** | HTTP, WebSocket | HTTPS, WebSocket |
| Конфигурация | Файл | **Декларативная (IaC)** | Код / YAML | Консоль, Terraform |
| Сложность | Средне-высокая | Высокая | Низкая | Низкая |
| Стоимость | Бесплатно | Бесплатно | Бесплатно | Оплата за запросы |

**Критерии для AdScale:** пик 18 000 RPS с запасом, HTTP/2 и gRPC, декларативная
конфигурация, работа в Kubernetes, встроенные Circuit Breaker и метрики.

**Выбор — Envoy:** проходит по всем критериям без плагинов; сложность эксплуатации
компенсируется готовыми модулями и поддержкой service mesh на этапе 2.
