# API Gateway для DSP-интеграции

## 1. Назначение и место

API Gateway — единая точка входа для внешнего трафика: DSP-партнёра (bid-request) и
рекламодателя (личный кабинет). **Документ описывает DSP-контур**; маршруты кабинета
не детализируются. Принимает `bid-request` по HTTPS, проверяет подлинность,
ограничивает частоту, маршрутизирует в Bidding Service и собирает метрики времени отклика.

```
DSP ──HTTPS──▶ [Балансировщик] ──▶ API Gateway (Envoy, 2+) ──HTTP/2──▶ Bidding Service (2+)
```

**Что Gateway делает:** аутентификация, ограничение частоты, маршрутизация, Circuit Breaker,
таймауты, TLS, метрики, логирование, отсечение перегрузки.
**Что не делает:** аукцион — Bidding Service, кампании — Campaign Service, разметка —
Delivery Service, финансы — Financial Service. Gateway остаётся «умной трубой» и не содержит
бизнес-логики.

## 2. Маршрутизация

Задача — направить трафик ставок в Bidding Service, скрыв от DSP топологию: адреса,
количество экземпляров, масштабирование и деплой.

| Поток | Куда | Поведение |
|---|---|---|
| Запросы ставок от DSP (`bid-request`) | Bidding Service, кластер `bidding` | Проксирование с таймаутом 70 мс |
| Проверка доступности | Локальный ответ Gateway | Не нагружает сервис |
| Запросы вне контура ставок | — | Отклоняются без проксирования |

**Версионирование:** версия OpenRTB определяется заголовком и передаётся в Bidding Service;
подключение новой версии не требует изменения маршрута.

**Балансировка:** `LEAST_REQUEST` между экземплярами Bidding Service. DSP обращается
к одному адресу и не знает, сколько экземпляров работает.

**Размер запроса:** тело `bid-request` ограничено; запросы сверх лимита отклоняются
без проксирования — защита от перегрузки разбором.

**Преобразование протокола:** снаружи — HTTPS с JSON по OpenRTB, внутрь — HTTP/2.
Gateway терминирует TLS и переключает протокол; Bidding Service не занимается внешним TLS
и версиями HTTP.

## 3. Ограничение частоты запросов

**Зачем:** защитить систему от перегрузки и справедливо распределить поток между партнёрами —
при пике 18 000 RPS один партнёр не должен вытеснить остальных.

| Уровень | Что ограничивается |
|---|---|
| Общий | Суммарный поток ставок от всех DSP — не выше пиковой ёмкости |
| Партнёр | Индивидуальный лимит по договору |
| Экземпляр Gateway | Локальный лимит, согласованный между экземплярами |

**Ключевое требование:** лимит общий для всех экземпляров Gateway. Без общего учёта
два экземпляра пропустят вдвое больше.

**Кратковременные всплески** выше среднего допустимы, но не увеличивают средний поток.

**При превышении** Gateway отвечает сразу, без проксирования. Очередь не накапливается:
запрос, отложенный сверх бюджета, всё равно не уложится в SLA, поэтому DSP фиксирует no-bid.

Без ограничения частоты перегрузка дошла бы до Bidding Service и убила бы SLA для всех DSP.

## 4. Аутентификация

**Зачем:** убедиться, что запрос пришёл от доверенного DSP, не изменён по пути и не является
повторным воспроизведением перехваченного запроса.

| Задача | Решение |
|---|---|
| Идентификация партнёра | Персональный ключ DSP |
| Целостность запроса | Подпись тела запроса секретом партнёра |
| Защита от повтора | Метка времени в подписи с допустимым окном |
| Дополнительно | Взаимный TLS для крупных партнёров, ограничение по IP |

**Требования:**
- секреты хранятся в защищённом хранилище, не в коде и не в конфигурации;
- ротация ключей без простоя;
- при неверной подписи запрос отклоняется на Gateway и не доходит до Bidding Service.

Все проверки выполняются на Gateway: Bidding Service получает уже проверенный запрос
и не тратит время на аутентификацию.

**Доверие:** Bidding Service повторно подпись не проверяет — это допустимо только
во внутренней доверенной сети (закрытый периметр). Если периметр нарушен, проверка
возвращается в сервис.

## 5. Паттерн Circuit Breaker (автоматический размыкатель)

**Зачем.** Если Bidding Service начал отвечать медленно или с ошибками, бесконечно
отправлять ему запросы нельзя: они копятся в очереди, ожидание растёт, деградация
передаётся дальше по цепочке. Размыкатель вовремя отключает проблемный сервис,
даёт ему восстановиться, а DSP сразу получает понятный ответ.

**Как работает — три состояния:**

| Состояние | Что происходит |
|---|---|
| **Замкнут** | Запросы идут в Bidding Service, Gateway считает долю ошибок |
| **Разомкнут** | Доля ошибок превысила порог — запросы не отправляются, DSP сразу получает отказ |
| **Проверка** | Через паузу Gateway пропускает несколько пробных запросов: успех → замкнут, ошибка → снова разомкнут |

**Пороги:**

| Правило | Значение | Почему так |
|---|---|---|
| Доля ошибок | 50% за 10 секунд | Единичная ошибка — норма; размыкать нужно при системной деградации |
| Минимум запросов | 20 | Не реагировать на случайные сбои при малом объёме |
| Пауза в разомкнутом состоянии | 30 секунд | Время на восстановление сервиса |
| Пробных запросов | 5 | Достаточно, чтобы понять, восстановился ли сервис |
| Таймаут одного запроса | 70 мс | Бюджет внутри SLA DSP — расчёт ниже |

**Расчёт таймаута 70 мс:**

```
SLA DSP:                 80 мс
− внешняя сеть DSP ↔ Gateway и обработка на стороне DSP: 10 мс
= бюджет Gateway:        70 мс
```

Внутри бюджета: обработка Bidding — 46–56 мс, сеть Gateway → Bidding — 1–2 мс,
запас — 12–23 мс на случайные колебания сети и непредвиденные задержки.

**Что получает DSP при разомкнутом состоянии:** быстрый отказ с указанием, когда
повторить. DSP фиксирует no-bid — простоя и штрафа нет. AdScale не накапливает очередь
и не деградирует дальше.

**Защита от переполнения** — отдельный механизм, не размыкатель: ограничение числа
одновременных соединений и ожидающих запросов, чтобы Gateway не накопил очередь.

## 6. Мониторинг и наблюдаемость

Gateway — единая точка наблюдения за внешним трафиком: метрики, логи, трассировки.

### 6.1 Метрики

| Метрика | Назначение |
|---|---|
| Пропускная способность (RPS) | Контроль нагрузки и приближения к 18 000 RPS |
| Время ответа Bidding Service (гистограмма) | Основной показатель SLA |
| Полное время от запроса до ответа | Включая сеть и Gateway |
| Ошибки Bidding (`5xx`) | Деградация сервиса |
| Доля no-bid | Качество аукциона и срабатывание защит |
| Отклонённые запросы | Работа ограничения частоты |
| Срабатывания размыкателя | Нестабильность Bidding Service |

**SLO и алерты:**

| Показатель | Порог | Действие |
|---|---|---|
| P95 всего времени отклика | > 70 мс 5 минут | Предупреждение |
| P95 | > 80 мс 2 минуты | Критический алерт: нарушение SLA DSP |
| P99 | > 150 мс | Критический алерт |
| Доля `5xx` | > 1% | Алерт |
| Доля no-bid по таймауту | > 5% | Алерт |

### 6.2 Логи

Единый формат для каждого запроса: идентификатор запроса, партнёр, версия OpenRTB,
статус, полное время ответа, время ответа Bidding, IP и user-agent.

Единый лог позволяет ответить на вопросы: сколько запросов от партнёра за час, где
теряется время, какие ответы дают ошибки. Без него данные пришлось бы собирать из всех
сервисов по отдельности.

### 6.3 Трассировка

Идентификатор запроса передаётся из Gateway в Bidding Service и далее в Campaign
и Delivery. По нему видно, на каком шаге возникла задержка.
