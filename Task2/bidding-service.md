# Bidding Service — спецификация сервиса ставок

## 1. Назначение и границы

**Bidding Service** — сервис, который принимает `bid-request`, подбирает кандидатов, проводит аукцион
и возвращает `bid-response`. Выделен из монолита первым, потому что находится на критическом пути
и сильнее всего ограничен по времени отклика.

### 1.1 Что входит в границы

| Функция | Описание |
|---|---|
| Приём `bid-request` | Валидация запроса, проверка обязательных полей |
| Подбор кандидатов | Отбор кампаний по таргетингу (гео, устройство, время, формат) |
| Аукцион | Расчёт ставок и выбор победителя; по умолчанию second price (тип — поле `at`) |
| Резервирование бюджета | Атомарное уменьшение доступного бюджета победителя |
| Формирование `bid-response` | Победитель, цена, ссылка на разметку |
| Обработка no-bid | Ответ без `seatbid`, если нет кандидатов или бюджета |
| Публикация событий | События ставок и результатов аукциона в Kafka |

**Вне границ:** Campaign Service (кампании, таргетинг), Delivery Service (разметка),
Financial Service (списания), Statistics / Analytics (события), Dashboard BFF (UI).
Соответствие — раздел 3.1 TO-BE: Ad Server и Auction Engine монолита объединяются
в Bidding Service, остальные компоненты остаются на своих местах.

## 2. Компонентная диаграмма

| Компонент | Ответственность | Зависимости |
|---|---|---|
| **Bid Request Handler** | Валидация `bid-request`, контроль `tmax`, формирование ответа | — |
| **Targeting Filter** | Отбор кандидатов по гео, устройству, формату, времени | Redis, Campaign |
| **Auction Engine** | Расчёт ставок, выбор победителя | Targeting Filter, Budget Reservation, Delivery (через Circuit Breaker) |
| **Budget Reservation** | Атомарное резервирование бюджета | Redis |
| **Event Publisher** | Публикация событий в Kafka | Kafka |
| **Cache Invalidator** | Инвалидация кеша по событию `campaign.updated` | Kafka, Redis |
| **Circuit Breaker** | Защита вызовов Campaign и Delivery | — |

Поток обработки: `bid-request` → Bid Request Handler → Targeting Filter → Auction Engine →
Budget Reservation → Bid Request Handler → `bid-response`. Событие публикуется
асинхронно, параллельно ответу, через Event Publisher.

**Cache Invalidator** работает вне потока запроса: читает `campaign.updated` из Kafka
и удаляет устаревшие ключи Redis. При недоступности Kafka кеш живёт до истечения TTL (5 минут).

Схема в формате PlantUML: `diagrams/component-bidding-service.puml`.

## 3. API

### 3.1 Внешний API — приём ставок

| Параметр | Значение |
|---|---|
| Протокол | HTTPS, JSON |
| Стандарт | OpenRTB 2.5 |
| Метод | `POST /rtb/bid` (маршрут AdScale, не из стандарта) |
| Вызывающая сторона | DSP-партнёр (через API Gateway) |
| Бюджет времени | Поле `tmax` в `bid-request`; сервис обязан ответить раньше |
| `tmax` по умолчанию | 80 мс, если поле отсутствует; максимум — 200 мс |
| Версия | `x-openrtb-version`, по умолчанию `2.5` |
| Размер тела | Не более 64 КБ |

**Вход:** `BidRequest` по OpenRTB 2.5. Обязательны `id`, `imp[]`, `site`/`app`;
архитектурно значимы `tmax` (бюджет времени) и `at` (тип аукциона: 1 — first price,
2 — second price).

**Выход:** `BidResponse` — `id`, `seatbid[]` (кампания, цена, разметка `adm`); при no-bid —
пустой `seatbid` и код причины `nbr`.

**Правила ответа:** ошибки зависимостей и превышение `tmax` не возвращаются как HTTP-ошибки —
сервис отвечает no-bid (`200` + `nbr`).

**Коды ответов:**

| Код | Когда | Кто формирует |
|---|---|---|
| `200` + `bid-response` | Ставка есть | Bidding Service |
| `200` + no-bid (`nbr`) | Нет кандидатов, бюджет исчерпан, таймаут, ошибка зависимости | Bidding Service |
| `400` | Невалидный `bid-request`: нет `id`, `imp` или `site`/`app` | Bidding Service |
| `401` / `403` | Ошибка аутентификации или ключ отозван | API Gateway |
| `408` | Timestamp запроса вне допустимого окна | API Gateway |
| `413` | Превышен размер тела (64 КБ) | API Gateway |
| `429` | Превышен лимит частоты | API Gateway |
| `500` | Непредвиденная ошибка сервиса (алерт) | Bidding Service |
| `503` | Circuit Breaker открыт | API Gateway |

### 3.2 Внутренний API — получение кампаний

| Параметр | Значение |
|---|---|
| Протокол | REST через ACL (этап 1) / gRPC (этап 2) |
| Метод | REST: `GET /campaigns/candidates` (этап 1); gRPC: `GetCandidates` (этап 2) |
| Вход | Таргетинг из `bid-request` (гео, устройство, формат, время) |
| Выход | Список кампаний со ставками, лимитами и ограничениями |
| Таймаут | 15 мс |

Кампании кешируются в Redis; внешний вызов Campaign выполняется только при промахе кеша.

### 3.3 Внутренний API — выдача разметки

| Параметр | Значение |
|---|---|
| Протокол | Internal Call (gRPC) |
| Метод | `DeliveryService.RenderCreative` |
| Вход | Идентификатор креатива, контекст показа |
| Выход | HTML/JS-разметка, URL отслеживания |
| Таймаут | 10 мс |

При таймауте Delivery сервис отвечает no-bid: без разметки показ невозможен, резерв
бюджета возвращается.

## 4. Зависимости

| Зависимость | Протокол | Назначение | Критичность | При отказе |
|---|---|---|---|---|
| Redis | Redis protocol | Кеш кампаний, счётчики бюджета | Критичная | no-bid: бюджет неизвестен, риск перерасхода |
| Campaign Service | REST через ACL (этап 1) / gRPC (этап 2) | Источник кампаний при промахе кеша | Высокая | Работа по кешу Redis; при пустом кеше — дефолтная ставка |
| Delivery Service | Internal Call (gRPC) | Разметка креатива | Средняя | no-bid: без разметки показ невозможен |
| Kafka | Kafka protocol | Публикация событий, инвалидация кеша | Низкая (асинхронно) | Буферизация событий в памяти; инвалидация — по TTL (5 минут) |

Financial Service и Statistics Service — **не прямые зависимости**: связь только через Kafka.
Bidding Service **не вызывает синхронно** Financial Service и не пишет в PostgreSQL —
ключевое отличие от Auction Engine монолита.

**Доверие:** подпись DSP повторно не проверяется — запрос приходит от API Gateway
по внутренней сети. Допустимо только в закрытом периметре.

## 5. Модель данных

Сервис **stateless**: собственной базы данных нет, между запросами состояние не хранится.

| Данные | Где хранятся | Кто владеет | Режим доступа |
|---|---|---|---|
| Кампании, таргетинг, ставки | Redis (кеш) + Campaign Service (источник) | Campaign Service | Чтение |
| Доступный бюджет | Redis (счётчик) | Financial Service (сверка) | Атомарное уменьшение |
| Остаток бюджета за период | Financial Service | Financial Service | Через Kafka-события |
| `bid-request` / `bid-response` | Не хранятся | — | Эфемерные |
| События ставок и аукционов | Kafka → Statistics Service | Statistics Service | Публикация |

### 5.1 Организация данных в Redis

**Кеш кампаний.** Читается по срезу таргетинга (гео, устройство, формат). TTL 5 минут —
компромисс между свежестью данных и нагрузкой на Campaign Service; при изменении кампании
инвалидируется событием `campaign.updated`. Стратегия — cache-aside: при промахе сервис
обращается в Campaign Service и заполняет кеш.

**Счётчик бюджета.** Атомарная проверка и уменьшение исключают перерасход при параллельных
запросах. Живёт в пределах периода кампании; инициализируется значением бюджетного лимита
кампании при её активации.

**Резерв бюджета.** Временная запись с TTL 60 секунд: если подтверждение не пришло,
резерв возвращается (компенсация).

### 5.2 Почему нет собственной БД

Bidding Service обрабатывает 18 000 RPS и не должен зависеть от синхронной записи в базу —
именно эта зависимость была причиной деградации Auction Engine. Данные кампаний принадлежат
Campaign Service, бюджеты — Financial Service; Bidding Service только читает кеш и резервирует
бюджет в Redis.

## 6. Нефункциональные требования

| Требование | Значение |
|---|---|
| Пропускная способность | 18 000 RPS (3 месяца), 50 000 RPS (год) |
| Время отклика | P95 ≤100 мс (общее), ≤80 мс для DSP |
| Состояние | Stateless, 2+ экземпляра за балансировщиком |
| Бюджет обработки | ~46 мс (кеш) / ~56 мс (промах); детали — TO-BE, раздел 7 |
